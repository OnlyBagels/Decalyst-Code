# CLAUDE.md — Decalyst-Code conventions

Read at the start of every Claude Code session in this repo. Conventions, style rules, and workflow rules that apply to every contribution.

## 1. Writing style — all comments, commits, READMEs, docs

All written content in this repo follows the 36 patterns from `github.com/conorbronsdon/avoid-ai-writing`. The principle: specificity and directness, no marketing voice.

### Vocabulary

Drop these and replace:

- "robust", "seamless", "elegant", "powerful", "vibrant", "thriving" — cut entirely or describe what the thing actually does
- "leverage" → "use"
- "utilize" → "use"
- "in order to" → "to"
- "due to the fact that" → "because"
- "serves as", "features", "boasts" → "is", "has"

### Constructions

Avoid:

- "Let's check...", "Let's explore..." — say what happens directly
- "It's worth noting that...", "Interestingly," — cut the filler
- "Moreover,", "Furthermore," — restructure or use "and"
- "Cleverly does X", "Elegantly handles Y" — describe the action, not your opinion of it
- Inline-header bullets like `**Speed:** improves by...` — write as prose
- "This allows for X" patterns — just say what it does

### Comments in code

- Default to none. Only write a comment when the WHY is non-obvious.
- Don't explain WHAT — names do that.
- Don't reference the current task or PR ("added for the X flow", "see issue #42").
- No "Generated by Claude" or AI attribution lines in source files.
- One short line when possible. Multi-paragraph docstrings only when documenting a public API others will read.

### Headings and rhythm

- Sentence case ("Tool registry"), not Title Case ("Tool Registry").
- Mix sentence lengths. Don't run 15–25 words for every sentence.
- Don't use five headers in 200 words.

### Self-check

If a block has 5+ vocabulary flags plus 3+ pattern categories, rewrite it. If it reads like marketing copy when you re-read it, rewrite it.

Source for the full pattern list: https://github.com/conorbronsdon/avoid-ai-writing

## 2. Git workflow

Two branches, `main` and `dev`.

- `main` — stable. Receives merges from `dev` after a phase is verified end-to-end.
- `dev` — active development. Every phase or bigger change is committed and pushed here.

### When to commit

A "phase or bigger change" is any of:

- A new file with non-trivial content
- A change to a public interface
- Completion of a unit from the build plan (tool registry, worker rewrite, etc.)
- A bug fix that affects runtime behavior

Don't batch unrelated changes into one commit.

### Commit messages

- Imperative mood: `add tool registry`, not `added` or `adds`.
- Follow the writing rules in section 1 — no hype words, no filler.
- One concern per commit.

### Verification before merging to main

- `npm run typecheck` passes
- `npm test` passes
- Manual smoke test if the change affects runtime behavior

Never force-push to `main`. Don't force-push to `dev` without checking first.
